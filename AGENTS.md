# @marianmeres/trend-chart — Agent Guide

## Quick Reference

- **Stack**: Deno, TypeScript, zero runtime deps, SVG. Published to JSR + npm.
- **Test**: `deno task test` | **Fmt/Lint**: `deno fmt && deno lint` | **npm build**: `deno task npm:build`
- **Publish gate**: `deno doc --lint src/mod.ts && deno publish --dry-run --allow-dirty`
- **Release**: `deno task rp` (patch) / `deno task rpm` (minor) — bumps + publishes to JSR and npm
- **Example**: `deno task example:build` (or `example:watch`), then `deno task example:serve` → http://localhost:8000

## Project Structure

```
src/
  types.ts          public option/data types + Scene model types
  scale.ts          data↔pixel mapping, domain clamping (pure)
  path.ts           visible slice, line/area SVG path strings (pure)
  ticks.ts          nice y ticks, x tick resolution (pure)
  zones.ts          zone gradient stops + band rects (pure)
  scene.ts          computeScene(): data+options → Scene (pure, THE core)
  render-string.ts  Scene → static SVG string (SSR)
  trend-chart.ts    TrendChart class: retained-mode DOM rendering, lifecycle
  gestures.ts       pan/wheel/pinch pointer handling (DOM, renders nothing)
  mod.ts            public exports
tests/              deno tests, one file per pure module (no DOM needed)
example/            interactive showcase page (not published to JSR)
  index.html        the page itself: markup + inline app logic (consumer-style)
  src/mod.ts        bundle entry — re-exports this lib + @marianmeres/vanilla
  themes/           design-tokens theme CSS + _generate.ts that emits it
  dist/bundle.js    generated by deno-build; excluded from fmt/lint
tmp/                gitignored working files (previews, plan docs)
```

## Architecture (single load-bearing rule)

Everything visual is computed in **pure code** (`computeScene()` → `Scene`
object: paths, labels, gradients, pixel points). Two thin consumers render it:

1. `trend-chart.ts` — builds the SVG tree **once**, redraws by patching
   attributes only (never `clear + rebuild`, never `innerHTML`).
2. `render-string.ts` — serializes a `Scene` to markup (SSR).

**Never** put `document`/DOM access into `scale/path/ticks/zones/scene/render-string` —
that breaks SSR and testability. New visual features go: compute in `scene.ts`
(+ types in `types.ts`) → render in BOTH consumers → test via scene/string.

## Critical Conventions

1. `deno fmt` settings are authoritative (tabs, width 90). Run before commit.
2. JSDoc is mandatory on every exported symbol **and every interface member**
   (`deno doc --lint src/mod.ts` must be clean — it is a JSR publish gate and
   the JSR docs score). Explicit return types everywhere (no "slow types").
   Runnable `` ```ts `` examples on the two entry points (`TrendChart`,
   `renderToString`) — elsewhere a one-line description is enough.
3. Pan/zoom state = `domainX` window; gestures only call `setDomainX` —
   they never render.
4. Colors go through `cssColor(name, fallback, useVars)` so CSS-var theming
   keeps working (`--trend-chart-*`).
5. No new runtime dependencies. Date/number formatting stays host-supplied
   (`formatX`/`formatY`) — no time logic in the lib.
6. Out of scope (do not add): multi-series, bar/pie, built-in tooltips,
   momentum panning, canvas renderer.
7. Interaction boundary — "the lib says where and fires when; the host says
   what". Points and annotations both ship geometry + pixel coords + callbacks;
   the host renders the note/tooltip. `Annotation.data` and `DataPoint.data` are
   opaque passthrough: never inspect (or serialize) either. Growing annotations
   into a note-rendering layer (popovers,
   rich text, flip positioning) is how tooltips creep back in via rule 6.

## Before Making Changes

- [ ] `deno task test` green; add/extend tests for pure-module changes
- [ ] `deno fmt && deno lint && deno doc --lint src/mod.ts` clean
- [ ] Visual change? Regenerate previews (`deno run -A tmp/previews.ts`) and
      check against `tmp/screenshots/*` (the acceptance references — local and
      gitignored, may be absent in a fresh clone); the `example/` page is the
      interactive counterpart — new options belong in its toolbar
- [ ] New/changed option? Update all four: `types.ts` JSDoc, `API.md` option
      table, README (if user-facing), `example/index.html` toolbar
- [ ] Keep README.md + API.md in sync with option/API changes
